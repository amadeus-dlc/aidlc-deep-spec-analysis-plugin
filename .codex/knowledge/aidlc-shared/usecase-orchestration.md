# ユースケースは処理の順序を調整する

ユースケースに置くのはフロー制御である。ドメインモデルから状態を取り出して業務上の判断・加工・演算を再構成しない。判断に必要な状態を所有する型へ、その仕事を依頼する。

## 責務の境界

| 場所 | 所有する責務 |
| --- | --- |
| ユースケース | Repository/Clientの起動順、成功失敗の伝播、ドメイン操作への依頼、保存成功を待って結果を返すこと |
| ドメイン | 適用可否・互換性・鮮度・到達性等の判断、検証の対象選択、診断の意味と順序、採番と帰属の整合、集計、不変変換 |
| インターフェイスアダプタ | 外部入力の復号、外部プロセス/プロトコルの解釈、表示DTOへの変換、パス/文字列/数値表現の取り出し、出力の描画 |

- `id()`・`irHash()`・`toArray()`等のgetterや変換口をユースケースから使って仕事を再構成しない。VOを返すgetterでも同じである。
- Resultの成功値を取り出して業務処理を組み立てない。成否の振り分けからモデル・検証結果・準備結果の操作へ依頼する。汎用Resultへ個別ドメインの知識を混入しない。
- ドメインが決めた次の段階に従ってI/Oを起動することと、ユースケース自身が適用条件を計算することを区別する。
- `match`のcallbackやapplication helperへ同じ判断を移しても、責務は移ったことにならない。
- クライアントが生の`exit/doc/note`等を返し、ユースケースに外部プロトコルを解釈させない。アダプタが型付きの観測結果へ変換し、その業務上の意味をドメインが決める。
- 保存結果には保存したドメインオブジェクトを運ぶ。プリミティブDTOへの分解は出力側のアダプタに置く。
- 共有のFinalizerはI/Oの調整を担当できる。そこへ業務判断・表示変換を集めない。domainへRepository/Clientを渡す構造にも変えない。

時計の観測や次のI/Oを開始できるかの実行制御と、打切りによりどの対象をどの診断として記録するかは別責務である。後者は検証計画・検証結果が所有する。

CQSは個々の操作で守る。照会と状態変更を分け、不変変換は新しい値を返す。CQRSや投影専用read-model層を、この責務分離の前提にしない。

## 確認

getterの静的検査と、業務判断の所有者を追うレビューを併用する。getter検出ゼロだけで合格とはしない。名前の変更、型消去、別helper経由、免除リストで規律を迂回せず、必要な仕事が型の公開操作として成立しているかを確認する。
